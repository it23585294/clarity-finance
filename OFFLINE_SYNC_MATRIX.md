## Scope and terminology

Source audit and repairs start at `8957e560c5fd6624edeaf31459d0a5527cd7b66b`. The authoritative requirement is FR19, requirements PDF page 4 section 4, with the existing-session/locally-available-data qualifications in section 6.6, pages 6-7. **Local acceptance is not cloud confirmation.** Offline below means a durable immutable proposal can be saved; its confirmed financial contribution does not change until acknowledgement. Editing/deleting a cached confirmed record requires its resolved version/timestamp. A new child, allocation or receipt cannot be based on an unconfirmed/uncached parent. Resolve a predecessor first; the app does not speculate about dependent balances or silently reorder competing mutations.

Evidence labels: **U** = executable unit/coroutine tests (real Preferences DataStore where indicated, fake or mocked remotes); **R** = local Firestore rules emulator; **D** = isolated Android execution. None means new live acceptance. Device transport tests explicitly use Firestore SDK disableNetwork/enableNetwork; process death uses an actual targeted force-stop between separate instrumentation invocations. Activity recreation is a different test.

## Process ownership and operating-system limits

`ClarityApplication` starts one Koin-singleton `SessionSyncCoordinator`. It observes the authenticated UID and owns independent financial, crypto, savings and recurring workers. `start()` is idempotent. The existing single DataStore and Task-retaining repository/remotes are process singletons. Production Goal/Recurring ViewModels observe and submit; their screen-owned worker flags are disabled. Isolated tests can still exercise their worker seams explicitly.

- **While the app process is running:** automatic reconciliation starts for the restored/current UID and polls/retries approximately every five seconds. Individual awaits are bounded; network, OS suspension and earlier outstanding Tasks can delay completion. No particular feature screen is required.
- **After reopening following process death:** Firebase restores its session and the Application starts the same workers over UID-scoped durable proposals. Stable IDs and immutable payloads are reused. The Android SDK cache is separate from the proposal store.
- **While the process is absent/force-stopped:** there is no running coordinator and no promise of immediate synchronization. No WorkManager dependency, background service or background-execution guarantee was added. Reopen the app to resume. A Firebase transaction already sent before an await/process interruption may nevertheless commit on the server; reconcile it first.
- Account changes cancel old workers/listeners without waiting for noncooperative old callbacks, clear forms/messages/rows, and use UID/generation guards. Old proposals remain scoped to their originating UID. Delayed-account list loading now immediately clears the old contribution rather than leaving it visible.

## Recovery and conflicts

New financial mutations keep immutable server receipts and per-record state pointers; deletes retire their record identities. Server rules validate both sides of receipt/state/business mutation and preserve the previous financial atomic protections. A missing document alone is never sufficient evidence to replay a deletable legacy create.

An acknowledged matching receipt means success even if the primary record subsequently changed or was deleted. `RetainedTasks` keeps the underlying Firebase Task across cancelled/timed-out awaits to avoid overlapping same-process attempts. A later account/auth/access error is uncertainty, not proof of failure. An online withdrawal transaction either reconciles success or installs an immutable fence that excludes any earlier in-flight transaction. Only acknowledged rejection/fencing permits dismissal and a fresh corrected proposal. Crypto exposes the same safe resolution action. Local decode/DataStore/bookkeeping failures are never classified as remote rejection.

Old EXPENSE/INCOME/CREATE_PROJECT/CREATE_MILESTONE/CANCEL_MILESTONE/PAYMENT_DIRECT/PAYMENT_MILESTONE records are promoted atomically with the original raw JSON retained. An absent deletable pre-protocol create remains uncertain: review history and use online safe withdrawal before intentionally recording a replacement with a new ID. Pre-protocol crypto JSON is compared as a typed immutable proposal without adding fields to its saved payload. Corrupt recovery data produces an error and is retained; no reader/writer silently substitutes an empty queue. Malformed private recovery data requires diagnosis rather than unsafe dismissal.

## Baseline defects repaired

The baseline expense create performed a network read before persistence; ordinary edit/delete and several project mutations had no durable proposal; legacy create completion accepted a local snapshot as cloud success; reconciliation compared too few fields; income decoding lost receipt links; income cancellation was swallowed; rate clearing was incomplete. Crypto could permanently classify broad errors as failed and only synchronized while observed. Goal/recurring synchronization depended on their screens. Old account rows could remain visible during a delayed replacement listener. Fixed catalogues/rules/domain checks prevented FR21.

These findings came from actual source and assertions, not only earlier milestone summaries. Existing goal expiry/in-flight safeguards, recurring immutable occurrences, exact arithmetic and financial security tests remain in place.
